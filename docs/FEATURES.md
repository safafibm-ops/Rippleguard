# Features

Every feature below is backed by working code — none of this is a mockup.
Where a feature has a real limitation, it's stated here rather than in the
fine print.

## 1. Dependency graph resolution

Resolves your full transitive dependency tree via a three-tier fallback:

1. **deps.dev `GetDependencies`** — authoritative, multi-ecosystem (npm,
   PyPI, Maven, Cargo, Go, NuGet).
2. **npm registry breadth-first search** with our own semver resolver
   (`ingest/ranges.py`), used automatically if deps.dev is unreachable.
3. **Lockfile versions only** (flat, no transitive edges) as a last resort.

Every scan reports which tier was actually used (`build_report.resolvers_used`
in the API, "How this scan was resolved" in the Risk Model tab), so you never
mistake a degraded scan for a complete one.

**Supported manifest formats:** `package.json` + `package-lock.json` /
`yarn.lock` / `pnpm-lock.yaml`, `requirements.txt`, `pom.xml`, and CycloneDX
or SPDX JSON SBOMs. GitHub repository URLs are fetched directly via the
GitHub Contents API.

## 2. Trust channel — inheritance exposure (the differentiator)

Five measured components, all shown with their exact evidence in the package
detail panel:

- **Version floatiness** — classifies the declared range (`^`, `~`, exact,
  wildcard, git ref) and discounts it if a lockfile with an integrity hash
  pins the resolution.
- **Install-time execution** — did the npm registry report a
  preinstall/install/postinstall script for this exact version?
- **Publisher fan-out** — the largest number of other registry packages any
  single maintainer of this package can also publish to (via npm's
  `search?text=maintainer:<user>`).
- **Publish recency** — how many days old is this version? Newer versions
  sit inside the community-detection window.
- **Downstream reach** — dependents inside your app plus across the public
  registry (deps.dev counts + ecosyste.ms lists).

## 3. Exploit channel

The channel every other SCA tool scores: OSV advisory severity (real CVSS
v3.1 base scores, parsed from the vector string — see `docs/ALGORITHMS.md`),
gated by an import-graph reachability proxy and dependency depth.

## 4. Rank inversion (the headline demo artefact)

Two full rankings of the same package set — one by CVSS, one by trust score —
rendered side by side with connector lines showing which packages moved.
The API separately reports the single largest movement and a "headline
inversion": a package with **zero** catalogued vulnerabilities that still
tops the trust ranking, because a CVSS-only tool would never surface it at
all.

## 5. Publisher blast-radius view

Every publishing identity seen in the scan, ranked by how many packages in
*this* application they can push a new version to, alongside how many
packages they control across the entire registry. This is the "one phished
account" view — nothing else in the free-tool space draws it.

## 6. Compromise propagation simulation

Pick any package and RippleGuard answers: *if this were compromised right
now, how far would it spread?* Implemented as a weighted shortest-path search
(maximising the product of transmission weights, not summing them) that
walks upward toward your application and reports:

- Packages and applications reached, at what depth
- A 0–100 blast-radius score with an itemised breakdown
- The top propagation paths, each annotated with its weakest link — i.e.
  exactly which edge pinning would cut

Clearly and repeatedly labelled as a **simulation**: nothing here asserts any
package is actually compromised.

## 7. Counterfactual remediation

Five modelled actions — pin, disable install scripts, upgrade to the OSV
fixed version, isolate/vendor, remove — each applied to a deep copy of the
graph, each re-scored by the **same pipeline** that produced the original
numbers (see `docs/ARCHITECTURE.md` for why this matters). The output table
shows before/after RippleGuard score, before/after blast radius, and which
channel each action actually fixes — because pinning and upgrading fix
different problems, and showing that trade-off explicitly is the point.

## 8. Deterministic explanations, everywhere

Every package gets a plain-English verdict and a bulleted evidence list
generated by template code (`explain/templates.py`) — no model call
required. This runs even with zero API keys configured.

## 9. Optional LLM narration, tightly grounded

If `ANTHROPIC_API_KEY` is set, the detail panel adds one short written
paragraph from Claude. The model receives **only** the evidence bundle (no
tools, no network, no broader context), and its output is programmatically
rejected if it names any package, CVE, or GHSA ID that is not present in that
bundle (`explain/llm.py::_validate`). It never produces a number that feeds
back into scoring. Turned off entirely by default.

## 10. Evaluation harness — does the trust ranking actually work?

Compares the trust-channel ranking, the blended ranking, and a CVSS-only
ranking against a seed list of packages named in real, published npm
compromise campaigns (`fixtures/iocs.json`), using ROC-AUC, average
precision, precision@k and recall@k — all implemented from scratch. This is
the one part of the project that produces a **measured result** rather than
a design claim: run it against the bundled sample and you get a real
delta, not an assertion.

## 11. Dependency graph visualisation

A hand-written force-directed SVG layout (see `docs/ARCHITECTURE.md`) coloured
by which channel dominates each package's risk, with install-hook packages
ringed, and click-through to the full evidence panel.

## 12. Full transparency on data-source health

Every scan reports, per upstream API, whether it was reachable, how many
calls succeeded, and the last error seen. When a source is down, the UI says
so explicitly rather than silently returning a partial answer that looks
complete.
